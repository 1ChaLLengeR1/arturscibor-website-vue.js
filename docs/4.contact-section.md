# Sekcja Kontakt — plan

Status: **plan zaakceptowany, implementacja w toku** (patrz commit po tym pliku).

## Punkt wyjścia

- Warstwa `src/api/contact/`, `src/api/admin/contact/` i `src/storage/contact/` **już istnieje i jest kompletna** — dokładnie ten sam stan co `work`/`tools` przed ich krokami UI. Gotowe akcje: `contact/apiCreateContact`, `apiGetContactCollection`, `apiDeleteContact`.
- Endpointy (z `docs/rest_api_docs.json`, zrzut ekranu):

  | Endpoint | Auth |
  |---|---|
  | `POST /api/v1/contact/create` | brak (Guest) |
  | `GET /api/v1/admin/contact/collection` | JWT |
  | `DELETE /api/v1/admin/contact/{contact_id}/delete` | JWT |

  Brak jakiegokolwiek endpointu do oznaczania wiadomości jako przeczytanej — `ContactResponseData.is_read` istnieje w odpowiedzi, ale nic go nie zmienia poza samym backendem. To nie jest coś, co przeoczyłem — po prostu nie ma takiego PATCH-a w API.

- **Obecne `Contact.vue` / `AdminContact.vue` (+ `AdminContact/Form.vue`, `LookMessage.vue`) są martwe**, jak reszta sekcji przed migracją: odwołują się do nieistniejącego modułu `admin/loadMessage`, robią surowe `fetchData` na pustych URL-ach, i — kluczowe — **publiczny formularz ma dziś upload zdjęć** (`v-file-input multiple`, "Dołącz zdjęcia strony, którą chcesz wycenić"), a nowy `ContactCreatePayload` **nie ma pola na plik w ogóle** (tylko `name`, `email`, `subject?`, `phone?`, `description`). Formularz trzeba przebudować od zera pod nowy kontrakt, nie tylko podłączyć pod działający store.

## Ustalenia

1. **Publiczny formularz** (`Contact.vue`) — wszystkie 5 pól: `name`, `email`, `subject` (opcjonalne), `phone` (opcjonalne), `description`. Bez uploadu plików — nowe API tego nie obsługuje. Zachowuję istniejący layout/animację (`slideContact`) i współdzielony `components/Contact/Header.vue` (bez zmian, działa poprawnie).
2. **Panel admina** (`AdminContact.vue`) — bez przełącznika PL/EN (w przeciwieństwie do Work/Tools) — wiadomości kontaktowe to zwykły tekst od gościa, nie `MultiLangText`, więc nie ma tu koncepcji języka do przełączania. Lista pokazuje `is_read` jako czysto informacyjny znacznik (kropka/badge) — bez możliwości zmiany z panelu, bo nie ma do tego endpointu.
3. **Widok szczegółów wiadomości** — modal (`v-dialog`, jak w Tools "Pokaż więcej"), nie panel rozwijany jak w Work/Tools Edit — tu nie ma nic do edycji, tylko podgląd + usuwanie, więc modal pasuje lepiej niż pełny scroll-to panel.
4. **i18n od razu** — `contact.*` (public) i `admin.contact.*` (admin), tak jak przy Tools.

## Mapowanie: funkcjonalność → plik

| Co | Plik | Uwaga |
|---|---|---|
| Publiczny formularz | `src/views/Contact.vue` | przepisany od zera, bez uploadu plików, dispatch `contact/apiCreateContact` |
| Widok admina | `src/views/admin/AdminContact.vue` | przepisany, lista + modal podglądu |
| Lista wiadomości (admin) | `src/components/AdminContact/ListMessages.vue` | nowy, zastępuje martwy `Form.vue` |
| Podgląd wiadomości (modal) | wewnątrz `AdminContact.vue` (`v-dialog`) | zastępuje martwy `LookMessage.vue` (bez karuzeli zdjęć — nie ma już zdjęć) |
| Do skasowania | `src/components/AdminContact/Form.vue`, `LookMessage.vue`, `scss/LookMessage.scss` | martwy kod, `admin/...` nie istnieje |
| Tłumaczenia | `src/utils/locales/{pl,en}.json` | `contact.*` (public) + `admin.contact.*` |

## Co NIE wchodzi w ten krok

- Oznaczanie wiadomości jako przeczytanej — brak endpointu w API.
- Filtrowanie listy w adminie (`ContactCollectionQuery` wspiera `is_read`/`created_from`/`created_to`/`limit`) — pobieramy całą kolekcję bez filtrów, jak w Work/Tools.
