# Sekcja Home — warstwa API

Status: **plan zaakceptowany, w trakcie implementacji warstwy `src/api/` (bez zmian w `.vue`)**.

## Ustalenia

- Struktura `src/api/` jest **po domenach backendu**, nie po stronach frontendu — `src/api/<domena>/get.ts` (publiczne) i `src/api/admin/<domena>/post.ts` (chronione JWT), oparte o wspólną warstwę `src/api/common/{fetch,post,types}.ts`.
- Backend nie ma domeny „home”. To, co dziś pokazuje `Home.vue` / `AdminHome.vue`, mapuje się na realne domeny backendu: `work`, `cv`, `aboutme` (zdjęcia portfolio) i generyczny mechanizm uploadu plików.
- Animacja „Jestem {{developer}}” i CRUD „Jobs” w adminie **nie mają dziś odpowiednika w API** (stary model to lista stringów, `Work`/`WorkItem` to firma + stanowisko + daty + skille). Ustalono: docelowo animacja ma być zasilana z `WorkItemResponseData.title` przez `GET /work/collection` — to jednak zmiana w `.vue` (`Home.vue`, `AddJobs.vue`, `AdminHome.vue`), robiona **w kolejnym kroku**, nie teraz.
- `AboutMe` to osobna, już istniejąca sekcja (`AboutMe.vue` + `AdminAboutMe.vue`, własne routy) — mimo pierwotnego podejrzenia, **nie jest częścią Home** jako widok. Jej endpointy (`GET /aboutme`, `PUT /admin/aboutme/update`, `POST`/`DELETE /admin/aboutme/images`) implementujemy już teraz w `src/api/aboutme/` i `src/api/admin/aboutme/`, bo Home potrzebuje `AboutMeResponseData.images` do zdjęć rotujących — samo podłączenie w `.vue` zostaje na później.
- **Odkrycie zmieniające zakres:** `PUT /admin/cv/upload` przyjmuje `{ file_id }` (JSON), a nie surowe bajty. Upload CV (i logo firmy, i zdjęcia AboutMe) wymaga więc przejścia przez generyczny handshake plików: `POST /admin/file/init` → `PUT /admin/file/{file_id}/upload` (raw bytes) → `PATCH /admin/file/{file_id}/confirm` → dopiero wtedy właściwy endpoint domeny (`/admin/cv/upload`, `/admin/work/{id}/logo`, `/admin/aboutme/images`...). To nie jest zasób jednej domeny, tylko wspólna podstawa używana przez wiele domen — dlatego mieszka w `src/api/common/file/{types,get,post}.ts`, obok `fetch.ts`/`post.ts`, a nie pod `admin/file/`.
- `GET /api/v1/cv` to nie jest zwykła koperta `ApiResponse` — sukces (200) zwraca surowy plik (FastAPI `FileResponse`), błąd (404/500) zwraca zwykły `ApiErrorResponse` w JSON. To jedyny endpoint w tym kroku, który nie może przejść przez `apiGet` ze wspólnej warstwy (ta zawsze robi `response.json()`); potrzebuje własnej, prostej implementacji w `cv/get.ts`.

## Mapowanie endpoint → plik

| Endpoint | Auth | Plik |
|---|---|---|
| `GET /api/v1/work/collection` (`lang` query) | brak | `src/api/work/get.ts` → `getWorkCollection` |
| `POST /api/v1/admin/work/create` | JWT | `src/api/admin/work/post.ts` → `createWork` |
| `PUT /api/v1/admin/work/{work_id}/update` | JWT | `src/api/admin/work/post.ts` → `updateWork` |
| `DELETE /api/v1/admin/work/{work_id}/delete` | JWT | `src/api/admin/work/post.ts` → `deleteWork` |
| `PUT /api/v1/admin/work/{work_id}/logo` | JWT | `src/api/admin/work/post.ts` → `attachWorkLogo` |
| `DELETE /api/v1/admin/work/{work_id}/logo` | JWT | `src/api/admin/work/post.ts` → `removeWorkLogo` |
| `POST /api/v1/admin/work/{work_id}/items` | JWT | `src/api/admin/work/post.ts` → `createWorkItem` |
| `PUT /api/v1/admin/work/{work_id}/items/{item_id}/update` | JWT | `src/api/admin/work/post.ts` → `updateWorkItem` |
| `DELETE /api/v1/admin/work/{work_id}/items/{item_id}/delete` | JWT | `src/api/admin/work/post.ts` → `deleteWorkItem` |
| `GET /api/v1/cv` (binarny plik) | brak | `src/api/cv/get.ts` → `getCv` |
| `PUT /api/v1/admin/cv/upload` (`{file_id}`) | JWT | `src/api/admin/cv/post.ts` → `uploadCv` |
| `GET /api/v1/aboutme` (`lang` query) | brak | `src/api/aboutme/get.ts` → `getAboutMe` |
| `PUT /api/v1/admin/aboutme/update` | JWT | `src/api/admin/aboutme/post.ts` → `updateAboutMe` |
| `POST /api/v1/admin/aboutme/images` | JWT | `src/api/admin/aboutme/post.ts` → `attachAboutMeImage` |
| `DELETE /api/v1/admin/aboutme/images/{file_id}` | JWT | `src/api/admin/aboutme/post.ts` → `detachAboutMeImage` |
| `POST /api/v1/admin/file/init` | JWT | `src/api/common/file/post.ts` → `initFile` |
| `PUT /api/v1/admin/file/{file_id}/upload` (raw bytes) | JWT | `src/api/common/file/post.ts` → `uploadFileBytes` |
| `PATCH /api/v1/admin/file/{file_id}/confirm` | JWT | `src/api/common/file/post.ts` → `confirmFile` |
| `DELETE /api/v1/admin/file/{file_id}/delete` | JWT | `src/api/common/file/post.ts` → `deleteFile` |
| `GET /api/v1/admin/file/collection` | JWT | `src/api/common/file/get.ts` → `getFileCollection` |

Każda domena z odpowiedziami JSON dostaje własny `types.ts` z konkretnymi aliasami na generyk z `src/api/common/types.ts`, np.:

```ts
export type WorkCollectionResult = ApiResult<WorkResponseData[]>;
export type CreateWorkResult = ApiResult<null>; // POST /work/create nie zwraca danych (pusty response)
```

## Co NIE wchodzi w ten krok

- Żadne zmiany w plikach `.vue` (Home.vue, AdminHome.vue, AboutMe.vue, AddJobs.vue, UploadFile.vue, Upload_information.vue) — obecny (zepsuty) kod zostaje nietknięty, aż zrobimy osobny krok podłączenia.
- Domeny spoza tego, co realnie zasila Home/AboutMe/CV/Work: `tools`, `projects`, `contact` — osobne, późniejsze kroki.
